# OT-002: API contract

## Why

As the developer building features on overkill-todo, I want the frontend's view
of the API to come from the backend's own description of it, so that a change to
a request or response shape breaks the build instead of breaking a Member's
session in production.

The backend already publishes an OpenAPI description, but nothing depends on it.
The frontend's request and response types are written by hand and kept in step
by memory. The description is also incomplete: 25 routes are served, but only 18
are described. The undocumented ones include the whole password-reset flow, the
magic-link sign-in and unlinking a Google account. The description also gets some
shapes wrong. For example, it marks optional request fields such as the Turnstile
token as required. And it says nothing about what error responses look like.

Auth is the only feature so far, so there are few types to convert and few habits
to change. Every feature added after this would add more hand-written types to
convert later.

## What Changes

- The published API description covers every route the backend serves. Any
  route deliberately left out is listed, with the reason.
- The description reports field presence and nullability as the backend actually
  sends and accepts them, and documents the error body for each error status.
- The description is committed to the repository and regenerated by one command.
  The full gate fails if the committed copy is stale.
- The frontend's API request and response types are generated from that committed
  description. Frontend code keeps its current type names, and they stay in sync
  with the generated types automatically.
- The full gate fails if the generated frontend types are stale, or if frontend
  code no longer type-checks against them.
- One deliberate behaviour change: a few routes rejected _malformed_ requests
  (bad JSON, missing or mistyped query or path parameters) with a plain-text
  body, and sometimes with 415 or 422. They now answer 400 with the standard
  JSON error body, like every other route. Well-formed requests are unaffected,
  and the frontend never sends malformed ones.
- Otherwise, no API behaviour changes.

## Capabilities

### New Capabilities

- `api`: the contract the backend HTTP API offers its clients: what it publishes
  about its routes, request and response shapes and errors, and how that
  description is kept true.

### Modified Capabilities

None.

## Appetite

One week.

## Out of Scope

- A generated request client. The frontend's hand-written HTTP client keeps its
  token refresh, CSRF retry and device-fingerprint handling. Typing its endpoint
  paths against the description is a possible follow-up.
- Versioning the API, or changing any route, status code or payload.
- Serving the description in production (it stays dev-only, as today).
- Removing request/response types that no route uses (e.g. profile update, email
  change). They aren't published, so they don't affect the contract.
- Contract testing against a running backend (checking responses against the
  description at runtime).

## Dependencies

None. No external services and no data migrations.

## Ready

- **Riskiest unknown:** two things. First, whether the description can follow the
  served routes automatically without changing how routes are protected (sign-in,
  CSRF, verified email, admin checks). Second, how far the hand-written frontend
  types have drifted from what the backend really sends. Each mismatch is a
  decision about whether the frontend or the description is wrong.
- **First slice:** the whole feature, which fits the appetite. It starts by
  deriving the description from the served routes, then generates frontend types
  from it early, so the size of the drift is known on day one.
