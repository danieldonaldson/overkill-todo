# Design: OT-011 API fuzzing

## Context

See `proposal.md` for the motivation. The current state that shapes the
approach:

- `backend/openapi.json` is generated by utoipa and committed (OT-002).
  `openapi.rs` already has unit tests over the generated description
  (`every_schema_ref_resolves`, `guards_document_their_statuses`, ...). The
  `Guarded` methods in `routes.rs` already add the 401/403 responses to every
  operation they protect, through `document()`.
- Eight handlers declare `security(("bearer_auth" = []))` by hand. No
  `securitySchemes` entry exists, and the backend never reads an
  `Authorization` header: it reads the session cookie (path `/api`), checks
  `X-CSRF-Token` against the CSRF cookie on state-changing requests (except
  `EXCLUDED_PATHS` in `middleware/csrf.rs`), and reads a refresh cookie on
  `/auth/refresh`.
- With `DEV_MODE=false` the backend refuses to start without SMTP, a Turnstile
  secret and MX validation (`main.rs`). With `DEV_MODE=true` it uses console
  email, no-op Turnstile and MX checks, and gives `test-*` addresses the fixed
  code `123456`. OT-004's seeding already relies on this.
- `DEV_MODE` changes three things a client can see: 5xx messages carry the
  internal error text (`error.rs`), cookies lack `Secure`, and the Swagger UI is
  served. 4xx bodies are identical in both modes.
- CI's backend job already has a Postgres service and a warm Rust cache.
  Commits go straight to `main`, and images are built only after a full CI run
  on `main` passes.

## Goals / Non-Goals

**Goals:**

- A fuzz run that is cheap enough for `just ci` and gives the same result each
  time on the same commit.
- The security description is derived from the guards that actually run, so it
  can't drift again.

**Non-Goals:**

- Getting the fuzzer to pass email-gated or OAuth success paths.
- Fuzzing through the Caddy/Traefik edge. The edge adds no API behaviour.

## Hypothesis

We believe most first-run failures will be **description drift** (missing
statuses, schema mismatches) rather than real defects. We also believe the
"valid data is accepted" failures, caused by validation rules the description
doesn't express, can be avoided by leaving that check out and adding cheap
constraints (`format: email`, `minLength`) where the description is simply
incomplete. Slice 1 tests this locally: run once, then sort every distinct
failure into *fix the description*, *fix the backend* or *tune the fuzzer*. We're
right if the list is small enough to clear within slice 1, about 30 distinct
failures or fewer. If it is much longer, we narrow the checks (for example,
schema conformance only on 2xx at first). We record that and push the stricter
checks to slice 2 instead of growing the appetite.

## Decisions

### 1. Schemathesis, from the OpenAPI description

Schemathesis generates requests from the committed `openapi.json` with
Hypothesis (the same property-testing model as proptest, including shrinking).
It has built-in checks for most of the spec's failure conditions, and Python
hooks for the rest.

*Alternatives:* RESTler (heavier, stateful-first, .NET, weaker checks for
response conformance); a hand-written proptest harness that drives the axum
router in-process (fast, no new toolchain, but we would rebuild request
generation from the schema ourselves); cargo-fuzz (wrong level, see the
proposal's Out of Scope).

### 2. Pinned through uv, in a top-level `apifuzz/`

`apifuzz/` gets a `pyproject.toml`, a `uv.lock` (with hashes) and `uv` pinned in
`mise.toml`. `[tool.uv] exclude-newer` matches the 24-hour release-age rule
used for npm. The directory mirrors `loadtest/`: `run.sh`, `hooks.py` and a
Schemathesis config file.

*Alternative:* the Docker image pinned by digest, like `vmalert-tool`. It is
simpler to pin, but the hooks file needs mounting, it must use host networking
to reach the backend, and it is awkward to run outside Docker. Either is fine.
uv wins because the hooks are ordinary Python that tooling can type-check.

### 3. Run in `DEV_MODE=true`, against a throwaway database

The backend can't start without its dev-mode no-op adapters unless real SMTP,
Turnstile and DNS are wired in, and CI shouldn't depend on those. Dev mode is
safe for the checks we need. It only changes 5xx text, and any 5xx already fails
the run (the dev text even makes the failure easier to read). A leak in a 4xx
message would look the same in production. Plain-HTTP cookies without `Secure`
are what a local HTTP client needs anyway.

`run.sh` creates `overkill_todo_fuzz_<pid>` on the existing Postgres, migrates
it, starts the backend binary on its own port (`FUZZ_API_PORT`, default 4399),
waits for `/api/v1/health/ready`, runs the fuzzer, then stops the backend and
drops the database from a `trap`, whatever the outcome. A start or readiness
failure exits non-zero before any fuzzing. The fuzzer reads the committed
`openapi.json`, not the served one, so it tests the contract clients are given.

*Alternative:* add a `FUZZ_MODE` that is production in every other way, with
only the adapters swapped. Rejected because it adds a production-adjacent
switch for no extra coverage.

### 4. Security requirements come from the guards

Remove the hand-written `security(...)` attributes. Register three schemes in
`openapi::finalize`: `session_cookie` (apiKey in cookie), `csrf_header` (apiKey
in header `X-CSRF-Token`) and `refresh_cookie` (on `/auth/refresh`). Then
`document()` in `routes.rs` adds the security requirement wherever it adds the
status: `require_auth()` adds `session_cookie`, and `require_csrf()` adds
`csrf_header` on the same method and path set it already uses for its 403. A
new `openapi.rs` test fails when any operation names a scheme that isn't defined
(the spec's "reference to an undefined scheme" gate). Regenerate the types with
`just api-types`. The frontend types don't change, because security doesn't
appear in `schema.d.ts` payload types.

This also gives Schemathesis what its `ignored_auth` check needs: it knows which
operations need credentials, and it sends them without credentials to confirm
they're refused.

### 5. Sign-in hook that recovers from lost sessions

`hooks.py` defines a Schemathesis auth provider:

- **Member:** registers `test-fuzz-<run>-<n>@example.test` through the real
  register → verify-email flow (code `123456`), signs in, and keeps the session
  cookie, the CSRF cookie and the CSRF header value.
- **Admin:** the same, then promoted with the same parameterised `UPDATE` that
  `just grant-admin` uses, against the fuzz database. It is used only for
  `/admin/*` operations.
- **Lost sessions:** an after-call hook marks the credentials stale on any 401
  from an authenticated case. The next case signs in a *new* Member. Signing in
  the same Member again isn't enough, because the fuzzer may have changed their
  password or scheduled their account for deletion.

Passes: **Visitor** (no auth provider, all operations) and **signed-in** (auth
provider, all operations, Admin credentials on admin routes). The Member-on-admin
case is covered by also running `/admin/*` with Member credentials and expecting
403.

### 6. Checks

- **Built in:** `not_a_server_error`, `status_code_conformance`,
  `content_type_conformance`, `response_schema_conformance`,
  `negative_data_rejection`, `ignored_auth`.
- **Not in slice 1:** `positive_data_acceptance`. It's the main source of the
  noise named as the riskiest unknown. Slice 2 reconsiders it.
- **Custom `error_body` check:**
  - Every response with status ≥ 400 must be JSON in the standard shape (`code`
    and `message`, both strings) or the verification error shape.
  - A malformed-input rejection must be 400, never 415 or 422.
  - `message` must not match a deny list of internal-text patterns: `sqlx`,
    `SQLSTATE`, `duplicate key`, `violates`, `relation "`, `panicked`,
    `src/…​.rs:`, `RUST_BACKTRACE`, `Internal error:`, `Database error:`.
  - Serde's descriptions of the client's own malformed JSON ("invalid type …
    at line 1 column 9") are allowed. They describe the request, not the server.

### 7. Excluded operations

- **`GET /auth/oauth/{provider}/callback`:** excluded, because it exchanges
  the code with Google. `GET /auth/oauth/{provider}` is fuzzed, since it only
  builds a redirect.
- **Health routes:** fuzzed, since they're cheap.

Exclusions are listed with a reason in the Schemathesis config, like OT-002's
exemption list.

### 8. Budgets and seeds

- **Short run (`just fuzz-api`, `just ci`, CI):** fixed seed, about 25 examples
  per operation per pass. Target: under 3 minutes in CI, including starting the
  backend. A fixed seed makes it repeatable, so it can't flake on `main`.
- **Nightly:** a new workflow `fuzz-nightly.yml` (cron plus
  `workflow_dispatch`), about 500 examples per operation, with a random seed
  printed in the job summary along with the reproducing requests.
  - GitHub's failed-scheduled-workflow email is the notification. Nothing else
    is needed for a solo project.
  - `just fuzz-api seed=<n> examples=<n>` reproduces a run locally.

In `ci.yml`, the fuzz run is a separate `api-fuzz` job gated on the existing
`changes.outputs.backend` filter, which already includes `openapi.json`. It
reuses the Postgres service definition and the Rust cache. A separate job keeps
coverage numbers and timings of the backend job clean.

## Risks / Trade-offs

- **Noise drowns the signal on the first run** → checks are staged (Decision 6),
  and the triage in slice 1 is the measurement (Hypothesis).
- **Argon2 makes sign-in slow, so re-authenticating after every destructive case
  makes the run slow** → re-authenticate only after a 401, cap re-registrations
  per run, and measure in slice 1. If it is still slow, run the destructive
  operations (delete account, password change/set, logout) in their own small
  pass.
- **Lockouts and cooldowns (verification attempts, resend) trip during the run**
  → they're documented statuses, so they pass conformance. Each re-auth uses a
  fresh address, so a locked-out Member doesn't block the run.
- **The deny list goes stale or matches too much** → it lives in one place in
  `hooks.py` with a unit test that has a sample of allowed and denied messages.
- **Dev mode hides a production-only behaviour difference** → there are only
  three known differences (Context). A new dev-mode branch in API behaviour
  would need an entry in Context. Noted in `backend/ARCHITECTURE.md`.
- **A new toolchain (Python/uv) in a Rust/TS repo** → it is confined to
  `apifuzz/`, pinned and locked, and installed by `mise install`. Nothing in the
  product depends on it.
