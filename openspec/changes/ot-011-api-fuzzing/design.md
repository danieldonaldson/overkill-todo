# Design: OT-011 API fuzzing

## Context

See `proposal.md` for the motivation. The current state that shapes the
approach:

- `backend/openapi.json` is generated by utoipa and committed (OT-002).
  `openapi.rs` already has unit tests over the generated description
  (`every_schema_ref_resolves`, `guards_document_their_statuses`, ...). The
  `Guarded` methods in `routes.rs` already add the 401/403 responses to every
  operation they protect, through `document()`.
- Eight handlers declare `security(("bearer_auth" = []))` by hand. No
  `securitySchemes` entry exists. The auth middleware still accepts
  `Authorization: Bearer <jwt>` before the session cookie (`extract_token`),
  but no client uses it: the web app sends only cookies, and only the backend
  integration tests send Bearer (Decision 4a removes it). Otherwise the
  backend reads the session cookie (path `/api`), checks
  `X-CSRF-Token` against the CSRF cookie on state-changing requests (except
  `EXCLUDED_PATHS` in `middleware/csrf.rs`), and reads a refresh cookie on
  `/auth/refresh`.
- With `DEV_MODE=false` the backend refuses to start without SMTP, a Turnstile
  secret and MX validation (`main.rs`). With `DEV_MODE=true` it uses console
  email, no-op Turnstile and MX checks, and gives `test-*` addresses the fixed
  code `123456`. OT-004's seeding already relies on this.
- `DEV_MODE` changes two things a client can see: 5xx messages carry the
  internal error text (`error.rs`), and the Swagger UI is served. Cookies are
  `Secure` in both modes (`__Host-` prefix, OT-010). 4xx bodies are identical
  in both modes.
- CI's backend job already has a Postgres service and a warm Rust cache.
  Commits go straight to `main`, and images are built only after a full CI run
  on `main` passes.

## Goals / Non-Goals

**Goals:**

- A fuzz run that is cheap enough for `just ci` and gives the same result each
  time on the same commit.
- The security description is derived from the guards that actually run, so it
  can't drift again.

**Non-Goals:**

- Getting the fuzzer to pass email-gated or OAuth success paths.
- Fuzzing through the Caddy/Traefik edge. The edge adds no API behaviour.

## Hypothesis

We believe most first-run failures will be **description drift** (missing
statuses, schema mismatches) rather than real defects. We also believe the
"valid data is accepted" failures, caused by validation rules the description
doesn't express, can be avoided by leaving that check out and adding cheap
constraints (`format: email`, `minLength`) where the description is simply
incomplete. Slice 1 tests this locally: run once, then sort every distinct
failure into _fix the description_, _fix the backend_ or _tune the fuzzer_. We're
right if the list is small enough to clear within slice 1, about 30 distinct
failures or fewer. If it is much longer, we narrow the checks (for example,
schema conformance only on 2xx at first). We record that and push the stricter
checks to slice 2 instead of growing the appetite.

### Outcome (slice 1, first runs, 2026-11-17)

Confirmed: the list was short, about 6 distinct failures, well under 30, and it
cleared within the slice. The noise came from the harness, not from validation
rules the description doesn't state. The first run (seed 1, 25 examples) had 17
failures from 3 causes in the Visitor pass. The signed-in pass couldn't run
until the harness was fixed, and then found 3 more.

- **Fix the backend (2):**
  - `POST /auth/oauth/device-fingerprint` gave a 500 that leaked `Internal
error: …` for a fingerprint with control characters. The value also went
    into `Set-Cookie` unchecked, so `;` could add cookie attributes. It is now
    validated as a 1–128 character token, gets a 400, and the schema says so.
  - Every described path answered other methods with axum's empty-bodied 405
    (15 of the 17 first-run failures). The router now has a JSON 405 fallback.
- **Fix the description (3):**
  - `POST /auth/refresh` didn't document its 400 for a missing
    `X-Device-Fingerprint`.
  - `GET /auth/oauth/{provider}` documented 302, but it sends 307.
  - `{provider}` path parameters were plain strings, so the fuzzer never
    reached a success path. They are now the `google | apple` enum.
- **Tune the fuzzer (≈7, all harness bugs):** credentials sent to public
  operations, so a sign-in 401 looked like a lost session. Sessions not cached
  (`refresh_interval = None` means "never cache"). A cached `None` shared with
  the Member key. Generated session cookies overriding the real one. Custom
  checks judging CORS preflights. Echoed input matching the deny list. Run-
  and server-specific values (pid-based emails, server UUIDs) varying the
  inputs between runs.

Before the harness fixes, the signed-in pass "passed" while its Member
operations only ever saw 401s. The per-operation 2xx counts in
`request_report` caught that. `positive_data_acceptance` stayed off as
planned. Slice 2 reconsiders it.

Checks verified to fail (each on a scratch change, then reverted):

- a description claiming a public route needs a session (Visitor pass,
  `ignored_auth`);
- the admin list with no role check (Member-on-admin pass, `admin_refused`);
- database error text in a 400 (`error_body`);
- bare axum `Json` (415, `error_body`).

Just removing `require_auth()` from a group does _not_ fail. The handler
extractors (`AuthUser`, `AdminUser`) enforce the same rules, so nothing is
exposed.

Session recovery was verified by invalidating every session in the fuzz
database 4 times during a signed-in run. The run signed up 4 more Members and
stayed clean, and `/auth/me` kept returning 200. The fuzzer itself rarely ends
its session, because it can't guess the current password that deletion and
password change need.

### Outcome (slice 2: `positive_data_acceptance`, 2026-11-17)

Turned on, it failed on 7 operations (seed 1, 25 examples).

- **Fix the description (3):**
  - `X-Device-Fingerprint` is now a required header on login, refresh,
    complete-signup and reset-password.
  - Verification codes have the pattern the server applies: six ASCII digits
    once separators are stripped, at most 32 characters.
  - Deletion's `confirmation` is required and must be `DELETE`. Every request
    without it was already refused.
- **400 by design, depending on state or configuration (6 operations):**
  - a well-formed but wrong, unknown or used code or token (verify-email,
    verify-reset-code, POST verify-magic);
  - a password requirement that depends on the account (delete, set-password);
  - providers that aren't configured (`apple` on OAuth start).

  A schema can't express these. The check stays **on** for every other
  operation, and is off for those six, each with its reason in
  `apifuzz/schemathesis.toml`.

Clean afterwards with seed 1 (25 examples) and seed 7 (150 examples).

## Decisions

### 1. Schemathesis, from the OpenAPI description

Schemathesis generates requests from the committed `openapi.json` with
Hypothesis (the same property-testing model as proptest, including shrinking).
It has built-in checks for most of the spec's failure conditions, and Python
hooks for the rest.

_Alternatives:_ RESTler (heavier, stateful-first, .NET, weaker checks for
response conformance); a hand-written proptest harness that drives the axum
router in-process (fast, no new toolchain, but we would rebuild request
generation from the schema ourselves); cargo-fuzz (wrong level, see the
proposal's Out of Scope).

### 2. Pinned through uv, in a top-level `apifuzz/`

`apifuzz/` gets a `pyproject.toml`, a `uv.lock` (with hashes) and `uv` pinned in
`mise.toml`. `[tool.uv] exclude-newer` matches the 24-hour release-age rule
used for npm. The directory mirrors `loadtest/`: `run.sh`, `hooks.py` and a
Schemathesis config file.

_Alternative:_ the Docker image pinned by digest, like `vmalert-tool`. It is
simpler to pin, but the hooks file needs mounting, it must use host networking
to reach the backend, and it is awkward to run outside Docker. Either is fine.
uv wins because the hooks are ordinary Python that tooling can type-check.

### 3. Run in `DEV_MODE=true`, against a throwaway database

The backend can't start without its dev-mode no-op adapters unless real SMTP,
Turnstile and DNS are wired in, and CI shouldn't depend on those. Dev mode is
safe for the checks we need. It only changes 5xx text, and any 5xx already fails
the run (the dev text even makes the failure easier to read). A leak in a 4xx
message would look the same in production. The `Secure` cookies are no problem
for a plain-HTTP client like the fuzzer: it sends them back regardless.

`run.sh` creates `overkill_todo_fuzz_<pid>` on the existing Postgres, migrates
it, starts the backend binary on its own port (`FUZZ_API_PORT`, default 4399),
waits for `/api/v1/health/ready`, runs the fuzzer, then stops the backend and
drops the database from a `trap`, whatever the outcome. A start or readiness
failure exits non-zero before any fuzzing. The fuzzer reads the committed
`openapi.json`, not the served one, so it tests the contract clients are given.

_Alternative:_ add a `FUZZ_MODE` that is production in every other way, with
only the adapters swapped. Rejected because it adds a production-adjacent
switch for no extra coverage.

### 4. Security requirements come from the guards

Remove the hand-written `security(...)` attributes. Register three schemes in
`openapi::finalize`: `session_cookie` (apiKey in cookie), `csrf_header` (apiKey
in header `X-CSRF-Token`) and `refresh_cookie` (on `/auth/refresh`). Then
`document()` in `routes.rs` adds the security requirement wherever it adds the
status: `require_auth()` adds `session_cookie`, and `require_csrf()` adds
`csrf_header` on the same method and path set it already uses for its 403. A
new `openapi.rs` test fails when any operation names a scheme that isn't defined
(the spec's "reference to an undefined scheme" gate). Regenerate the types with
`just api-types`. The frontend types don't change, because security doesn't
appear in `schema.d.ts` payload types.

This also gives Schemathesis what its `ignored_auth` check needs: it knows which
operations need credentials, and it sends them without credentials to confirm
they're refused.

### 4a. The backend stops accepting Bearer tokens

The description must not describe a method the backend doesn't accept, and the
backend shouldn't accept one the description doesn't state. Bearer is unused by
any client and is weaker than the cookie: the cookie is `__Host-`-prefixed,
`HttpOnly` and bound to the CSRF token, while a Bearer token is whatever a
script can read. So `extract_token` reads only the session cookie, and
`authorization` leaves the CORS allowed headers. A request that sends only a
Bearer token gets the same 401 `token_missing` as one that sends nothing. The
integration tests send the session cookie instead.

_Alternative:_ describe Bearer as a second scheme. Rejected because it keeps an
unused way in, and the fuzzer would have to cover both.

### 5. Sign-in hook that recovers from lost sessions

`hooks.py` defines a Schemathesis auth provider:

- **Member:** registers `test-fuzz-<run>-<n>@example.test` through the real
  register → verify-email flow (code `123456`), signs in, and keeps the session
  cookie, the CSRF cookie and the CSRF header value.
- **Admin:** the same, then promoted with the same parameterised `UPDATE` that
  `just grant-admin` uses, against the fuzz database. It is used only for
  `/admin/*` operations.
- **Lost sessions:** Schemathesis 4's own reactive re-auth does this, so no
  after-call hook is needed. Sessions are cached for the run. On a 401 from an
  authenticated case it drops the cached session, calls the provider again and
  replays the request once. The provider signs in a _new_ Member, because
  signing in the same Member again isn't enough: the fuzzer may have changed
  their password or scheduled their account for deletion. Sign-ups are capped
  per run (`FUZZ_MAX_SIGNUPS`), and Schemathesis stops re-authenticating on an
  operation whose 401 survives a fresh session (a wrong current password).
- **Only protected operations get credentials.** The provider returns none for
  operations whose security doesn't name `session_cookie`. Otherwise a public
  route's own 401 (a wrong password at sign-in) looks like a lost session.
  Public operations get their own cache key, because Schemathesis caches the
  `None` per key.
- **Credentials are never generated** (`with-security-parameters = false`).
  Generated session cookies replaced the real one, so signed-in cases never
  reached a handler. Missing and invalid credentials are still sent, by the
  Visitor pass and by `ignored_auth`'s probes.
- Test Members are named per pass, not per run (`test-fuzz-<pass>-<n>`). The
  database is new every run, and Schemathesis reuses values it saw in
  responses, so a varying email would vary the requests (Decision 8).

Passes, each its own Schemathesis run: **Visitor** (no auth provider, all
operations), **signed-in** (auth provider, all operations, Admin credentials on
admin routes) and **Member on admin** (Member credentials on `/admin/*`, where
every response must be 403).

### 6. Checks

- **Built in:** `not_a_server_error`, `status_code_conformance`,
  `content_type_conformance`, `response_schema_conformance`,
  `negative_data_rejection`, `ignored_auth`.
- **Not in slice 1:** `positive_data_acceptance`. It's the main source of the
  noise named as the riskiest unknown. Slice 2 turned it on, except for six
  operations whose 400s depend on server state (see Hypothesis outcome, slice 2).
- **Custom `error_body` check:**
  - Every response with status ≥ 400 must be JSON in the standard shape (`code`
    and `message`, both strings) or the verification error shape.
  - A malformed-input rejection must be 400, never 415 or 422.
  - `message` must not match a deny list of internal-text patterns: `sqlx`,
    `SQLSTATE`, `duplicate key`, `violates`, `relation "`, `panicked`,
    `src/…​.rs:`, `RUST_BACKTRACE`, `Internal error:`, `Database error:`.
  - Serde's descriptions of the client's own malformed JSON ("invalid type …
    at line 1 column 9") are allowed. They describe the request, not the server.

Added while implementing slice 1:

- **`csrf_enforced`** (signed-in pass): when a state-changing request that
  needs the CSRF header succeeds, it is sent again without the header and must
  get 403. `ignored_auth` drops _all_ credentials at once, so it never tests a
  valid session without the CSRF header.
- **`admin_refused`** (Member-on-admin pass): every response to a request that
  carried the Member's session is 403.
- **`request_report`**: prints the requests (and 2xx/3xx responses) per
  operation, and a digest of the generated inputs, so two runs can be compared.
- The custom auth checks judge only the operation's own method. The coverage
  phase also sends other methods. OPTIONS is answered by the CORS layer, and
  the rest get the JSON 405, which `error_body` still checks.
- `error_body` ignores a deny-list match that is the client's own input echoed
  back ("Unknown provider: SQLSTATE" for the path `/oauth/SQLSTATE/unlink`).

### 7. Excluded operations

- **`GET /auth/oauth/{provider}/callback`:** excluded, because it exchanges
  the code with Google. `GET /auth/oauth/{provider}` is fuzzed, since it only
  builds a redirect.
- **Health routes:** fuzzed, since they're cheap.

Exclusions are listed with a reason in the Schemathesis config, like OT-002's
exemption list.

### 8. Budgets and seeds

- **Short run (`just fuzz-api`, `just ci`, CI):** fixed seed, about 25 examples
  per operation per pass. Target: under 3 minutes in CI, including starting the
  backend. A fixed seed makes it repeatable, so it can't flake on `main`.
- **Nightly:** a new workflow `fuzz-nightly.yml` (cron plus
  `workflow_dispatch`), about 500 examples per operation, with a random seed
  printed in the job summary along with the reproducing requests.
  - GitHub's failed-scheduled-workflow email is the notification. Nothing else
    is needed for a solo project.
  - `just fuzz-api seed=<n> examples=<n>` reproduces a run locally.

What makes a run repeatable (verified: two runs on the same commit print the
same input digest for every pass):

- a fixed seed;
- one worker;
- no example database;
- fixed test-Member names;
- a digest that masks server-assigned UUIDs, which Schemathesis learns from
  responses (a real user's ID in a role change) and which differ on every
  fresh database.

Measured locally: about 20 s for all three passes, including the backend start.

In `ci.yml`, the fuzz run is a separate `api-fuzz` job gated on the existing
`changes.outputs.backend` filter, which already includes `openapi.json`. It
reuses the Postgres service definition and the Rust cache. A separate job keeps
coverage numbers and timings of the backend job clean.

## Risks / Trade-offs

- **Noise drowns the signal on the first run** → checks are staged (Decision 6),
  and the triage in slice 1 is the measurement (Hypothesis).
- **Argon2 makes sign-in slow, so re-authenticating after every destructive case
  makes the run slow** → re-authenticate only after a 401, cap re-registrations
  per run, and measure in slice 1. If it is still slow, run the destructive
  operations (delete account, password change/set, logout) in their own small
  pass.
- **Lockouts and cooldowns (verification attempts, resend) trip during the run**
  → they're documented statuses, so they pass conformance. Each re-auth uses a
  fresh address, so a locked-out Member doesn't block the run.
- **The deny list goes stale or matches too much** → it lives in one place in
  `hooks.py` with a unit test that has a sample of allowed and denied messages.
- **Dev mode hides a production-only behaviour difference** → there are only
  two known differences (Context). A new dev-mode branch in API behaviour
  would need an entry in Context. Noted in `backend/ARCHITECTURE.md`.
- **A new toolchain (Python/uv) in a Rust/TS repo** → it is confined to
  `apifuzz/`, pinned and locked, and installed by `mise install`. Nothing in the
  product depends on it.
